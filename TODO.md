# OpenVerse — задачи

## Сейчас — realtime / WebSocket

### Поток данных

```text
Действие пользователя → команда на backend → валидация и запись в БД
→ domain-событие по WebSocket → dispatcher на frontend → обновление нужного UI
```

- Команда выражает намерение пользователя: сейчас, например, `MessageSend`.
- Событие описывает уже произошедший факт: `message.created`, `message.updated`, `message.deleted`.
- Backend — источник истины. После перехода на страницу данные всегда загружаются из БД по HTTP; WebSocket только актуализирует уже открытую страницу.

### Backend: подключения, события и защита

- [x] Переделать `ConnectionManager` для нескольких вкладок: хранить `dict[UUID, set[WebSocket]]`, добавлять и удалять конкретный сокет, считать пользователя online, пока его множество сокетов не пусто.
- [x] Вызывать `disconnect(user_id, websocket)` из `endpoint.py`; после `discard()` удалять ключ пользователя только при пустом множестве. Не закрывать сокет повторно в обработчике `WebSocketDisconnect`.
- [x] Исправить ограничение `MAX_CONNECTIONS_PER_USER`: проверять `>=`, не добавлять отклонённый сокет и сразу завершать endpoint. Close code `1013`, frontend на него не переподключается.
- [x] Не ограничивать HTTP при превышении лимита WebSocket: шестая вкладка должна открываться и работать без realtime-обновлений.
- [x] После успешного изменения БД публиковать domain-событие всем нужным сокетам пользователя — рассылка идёт только после `COMMIT`. Стабильные `type`: `message.created`, `message.updated`, `message.deleted`.
- [x] Каждая WS-команда выполняется в своей транзакции (`factory.open_services`); ошибки превращаются в `command.error` и не рвут соединение; сбойный сокет получателя не прерывает рассылку.
- [x] Лимит размера payload и валидация схемы команд.
- [ ] Лимит частоты входящих команд (rate limit). Frontend не является границей безопасности.
- [x] Heartbeat: клиент шлёт текстовый кадр `ping`, сервер отвечает `pong`; нет кадров дольше `WS_IDLE_TIMEOUT_SECONDS` (60 с) — закрытие `4408`. `away` — отдельный продуктовый статус, не следствие heartbeat.
- [x] Адрес `/ws`, пользователь берётся из токена. Ошибка токена — закрытие `4401` после accept (браузер видит код); истечение токена во время соединения — тоже `4401`. Чужой Origin — `1008` до accept.
- [ ] При запуске нескольких процессов/контейнеров перенести координацию подключений и presence из памяти процесса в Redis.

## Сейчас — frontend (отдельный сервис `frontend/`)

Backend — чистый API. Старый Jinja-фронтенд удалён из backend; последнее его состояние — коммит `c287824` (`backend/src/templates`, `backend/src/static`), оттуда можно переносить логику.

### Структура

```text
frontend/src/
  app/          # точка входа, роутер, провайдеры
  shared/
    api/        # http.ts (cookie, 401 → /auth/refresh → повтор), ws.ts (reconnect с backoff), schema.d.ts
    ui/         # общие компоненты
    lib/        # форматирование дат, склонения
  entities/     # user, chat, message: типы и маленькие компоненты
  features/     # login, send-message, mark-read, open-direct-chat
  pages/        # LoginPage, MessengerPage, FriendsPage, ProfilePage
```

Импорт только сверху вниз: `pages → features → entities → shared`.

### Задачи

- [ ] Tailwind CSS.
- [ ] Прокси Vite: `/auth`, `/users`, `/chat`, `/ws` → `localhost:8000` (один origin, cookie и WS без CORS).
- [ ] Типы из OpenAPI (`openapi-typescript` по `/openapi.json`).
- [ ] TanStack Query для HTTP-данных; события WebSocket обновляют кэш запросов.
- [ ] WS-клиент (`shared/api/ws.ts`), одно соединение на вкладку в `RealtimeProvider`, открывается после входа, закрывается при выходе:
  - `ping` каждые 25 с; нет `pong` — переподключение;
  - `4401` → `/auth/refresh` и сразу переподключиться (при неудачном refresh — на экран входа);
  - `4408` и сетевые обрывы → backoff 1 с, 2 с, 4 с … до 30 с;
  - `1000`, `1008`, `1013` → не переподключаться;
  - события обновляют кэш TanStack Query; перенести `event_manager.js` из `c287824`.
- [ ] Мессенджер: список чатов с превью из `chat.last_message`; история через `useInfiniteQuery` — `GET /chat/{id}/messages`, прокрутка вверх `?before=<id первого>`, пока `has_more`.
- [ ] После переподключения WS догружать пропущенное: `?after=<id последнего>` в цикле, пока `has_more`.
- [ ] Идемпотентность: не добавлять сообщение дважды (оптимистичная отрисовка + событие).
